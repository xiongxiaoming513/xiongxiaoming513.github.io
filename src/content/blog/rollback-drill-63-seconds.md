博客上线第二天，我在 `runbooks/rollback.md` 里写下「回滚约 40 秒」。

写完自己都笑了——这个数字是猜的。

静态站没有灰度、没有后端，回滚理论上就是「再发布一次」。但理论上不算数，所以我决定真弄坏一次。

## 怎么弄坏

首页的 tagline 是 `src/consts.ts` 里的一行字符串：

```ts
tagline: '写代码，也写字。记录那些想清楚了的事。',
```

改成一句明显不属于这里的话：

```ts
tagline: '【回滚演练】这段文字不应该留在线上。',
```

提交、推送，剩下的交给流水线。如果一切正常，半分钟后全世界都能看到这句话——包括我自己。

## 时间线

| 时间 | 事件 |
| --- | --- |
| 10:34:51 | 坏提交推送 |
| 10:34:52 | GitHub Actions 开始构建 |
| 10:35:25 | 部署完成，**坏文案上线**（33 秒） |
| 10:35:46 | 执行 `git revert` 并推送 |
| 10:36:28 | 部署完成，**线上恢复**（42 秒） |

坏版本暴露了 **63 秒**，回滚本身 42 秒。两条命令：

```bash
git revert --no-edit <坏提交>
git push origin main
```

## 中间出了个岔子

写演练脚本的时候，我少写了一行变量赋值。

结果是：坏版本推送成功、部署成功、线上真的被我改坏了——然后脚本在计算耗时的时候崩了。

也就是说，**你用来救火的那套东西，本身也可能坏。**

最后是手工补的 revert。教训很朴素：演练脚本要先测，不能现写现跑。这件事我没有悄悄跳过，而是写进了演练记录的「发现的问题」。因为如果连演练都掩盖失误，那演练就没有意义。

## 真正贵的是什么

恢复只用了 42 秒。但这次是「我正盯着看」，所以 30 秒就发现不对。

如果没有人在看呢？

静态站没有监控，页面崩了不会有人告诉你。回滚能力再强，也得先知道「该回滚了」。所以事后补了两样东西：

- **部署后自动冒烟**：7 项检查，0.5 秒跑完，失败则整个工作流红灯
- **每 6 小时可用性检查**：跑同样的冒烟，挂了会发邮件

到这里链路才算闭合：**发布 → 验证 → 发现 → 回滚**。回滚只是最后一环，前面每一环都可能更贵。

## 一个反直觉的结论

做这次演练之前，我以为要验证的是「回滚快不快」。

做完发现，真正需要验证的是「**从出问题到有人知道，中间隔多久**」。

前者取决于工具链，后者取决于你有没有在链路上放一双眼睛。静态站能把回滚压到一分钟以内，但如果没人发现，那一分钟也只是个好看的数字。

## 建议

如果你有自己的线上项目，找个不出事的时间，故意弄坏一次。

不是为了测试「怎么回滚」——那大概率没你想的那么难。是为了知道：关掉监控、关掉告警、没人盯着的时候，你的系统能撑多久。

我这次的答案是 63 秒。下次不一定。
